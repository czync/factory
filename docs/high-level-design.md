# Migration Factory 高层设计

## 系统分工

Factory 将迁移方法、跨系统执行和证据归集放在同一条交付流程中。应用团队负责具体迁移，Factory Core 维护模板、共享能力和版本，平台工作线提供身份、环境、数据库和 CI/CD 能力。

| 组成 | 职责 |
| --- | --- |
| 工作台 | 确认范围、派发或打开 Agent 任务、处理待办与异常。SME 确认业务规则，迁移 lead 查看应用及 Wave 的进展、依赖和阻塞 |
| 后台服务 | 实例化版本化模板、计算前置条件、跟踪任务、同步外部结果、执行证据关卡与发布对账。数据库保存迁移任务、关联记录和证据状态 |
| MCP 与 Agent Skills | MCP 提供受控的任务领取、上下文读取、草稿与结果提交、问题上报。Skills 提供工作方法、工具入口和验证说明 |
| 作业库 | 用企业 GitHub 管理模板、Skills、检测脚本、申请模板、验证器和已验证方案。正在执行的应用绑定具体版本 |
| 现有系统 | Jira 保存任务与问题，GitHub 保存代码和 PR，Harness 执行构建、测试与部署，Artifactory 保存制品，TFE 执行基础设施工作，ServiceNow 和 SailPoint 办理请求与审批，Confluence 和 SharePoint 保存已有文档 |

## 迁移路径与工作包

- **As-Is** 保持功能及架构，按需选用七项平台改造。通用阶段为 Intake → Discovery → Spec → Build → Verify → 按需生产并行 → Cutover → Decommission。Onboarding 从 Intake 或 Discovery 并行启动。技术改造遵循可复现构建 → 旧系统基线 → 改造的顺序。
- **Modernize** 沿用共同阶段，增加旧代码逆向、业务规则提取、架构重建与业务等价性验证。Agent 按业务场景、交易流、报表或批处理归组规则草稿，提供输入、逻辑、输出及原始依据。SME 在工作台确认或提出异议。
- **Retire** 走 Intake → Discovery → Decommission，确认下游依赖解除、数据保留及下线审批。

七项改造包括密钥迁移（Vault／CyberArk）、Harness 接入、容器或 VM 部署、企业文件传输、AutoSys 调度、Sybase → Oracle、Solaris／Windows → Linux。每个工作包包含适用性和前置检测、人工操作指南与 Skill、可调用的脚本或申请模板、完成证据及已验证方案。首版可由人执行并登记证据，再逐步加入 AI 辅助和确定性自动化。

公共 Onboarding 工作包组织环境、身份组与映射、资源初始化、网络及运行准备。Factory 预填并发起已授权的请求，外部系统审批。无接口的步骤可提供预填内容和办理入口。工单获批后，后台再收集目标环境的检查结果来确认资源实际可用。

## 任务、外部事实与问题闭环

后台以迁移任务 ID 关联应用、工作包版本、Jira、PR、构建提交、Harness 运行和验收证据。Jira、GitHub 和 Harness 分别提供各自的原始记录，Factory 依据这些记录计算交付状态。界面与 MCP 使用同一套权限和状态规则。

Factory 发起跨系统操作时，建议先记录操作意图，再调用外部接口并回填外部 ID 和结果。Webhook 或定时同步负责收集外部发生的事件，并通过幂等键、去重和对账恢复中断的操作。这里的“双写”指内部留痕与外部业务记录互相可核对，跨系统请求按可重试操作处理。

Jira 可使用专门的 Migration Problem 类型。优先关联现有 Issue，候选触发来源包括：

- **Red → Green**。相关构建、扫描或比对失败，修复后同项检查通过时，将失败记录、修复 PR 和通过结果关联起来，生成待确认的解决草稿。
- **Agent 上报**。通过 MCP 提交环境阻塞、兼容性或配置问题及已尝试的排查。
- **预检与工单异常**。从资源探测和外部请求中记录实际阻塞，并交给对应负责人。

问题一旦识别即可记录，修复完成后补充 Solution 和验证。共享方案由 Factory Core 评估适用条件，纳入作业库。执行记录和经验沉淀可引用日志、PR 和构建证据，具体内容按来源权限和数据分类处理。

## 依赖、关卡与发布

- **依赖与配置**。记录应用对库表、调度作业、文件通道、队列和配置的依赖，以及来源、责任人与所属 Wave。配置记录可引用 Vault 路径。关键数据先迁移并经验证，依赖应用才能切换。未知归属需显式展示。
- **阶段关卡**。按模板版本核验证据，保留规则版本、结果和人工决定。日常 Develop 工作以反馈为主，正式发布晋级时核对基线、独立 Review、扫描和比对。豁免由授权人说明范围、理由、补偿措施及有效期。
- **发布证据链**。人从工作台请求 Develop → Release，Factory 校验并创建发布 PR，人工 Review 和合并。Harness 构建 Release 制品，UAT 与 PROD 使用同一不可变制品。授权人员在 Harness 执行生产部署，Factory 对账并由人发起 Release → master 更新。实际强制拦截取决于 Harness 发布流程是否接入检查记录。
- **权限**。工作台和 MCP 在服务端区分可执行动作。Agent 按获准工程身份开展开发工作，业务事实确认、签字、豁免和发布决定由授权人员完成。发布 PR 与日常开发 PR 使用各自的权限边界。
- **审计与度量**。记录发起者、执行者、时间、来源、规则版本和外部引用。从真实活动派生等待、进度、返工及缺陷指标。成本汇总标明可取得的来源和覆盖范围，工时与共享费用口径待确认。

## 推进顺序

先建立三条最小模板及工作包目录，与 W0 的真实迁移一起验证。M3–M5 验证首个 Agent 接入、Onboarding 请求跟踪和证据归集。M6–M7 验证 W0 发布和同制品对账。M8–M13 扩展七项工作包，形成 As-Is 标准，并按试点反馈完善 SME 确认及度量。后续 Wave 推广复用和跨应用协调。

工作台派发、IDE 领取和远程启动的具体接入方式，以及自动建单、发布拦截和跨 Wave 数据就绪证据的可用性，均以企业实例试点结果为准。
